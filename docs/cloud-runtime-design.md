# 后端运行与云迁移设计

版本：1.0 · 日期：2026-10-10 · 当前状态：本地可部署基座，尚未迁入云环境。

## 1. 部署目标

后端保持单个模块化 Node.js 服务，外接 PostgreSQL。阶段 D 再增加兼容 S3 的私有对象存储和任务队列。小程序、Web 和 App 共用同一 HTTPS API，不在云服务器上运行多套业务后端。

```text
公网 HTTPS / WAF
       ↓
反向代理或云负载均衡
       ↓
YOUAI API（至少两个可替换实例）
       ↓
托管 PostgreSQL（优先）
       ↓
对象存储与任务队列（阶段 D）
```

云厂商在迁移时根据地区、备案、微信合法域名、托管数据库和对象存储成本选择。应用只依赖标准容器、PostgreSQL 16+ 和 HTTPS，因此不把业务代码绑定到厂商专有运行时。

## 2. 当前运行基座

- `backend/server.js`：进程入口和优雅停机。
- `backend/http-server.js`：`/health/live`、`/health/ready`、请求标识和统一 JSON 错误。
- `backend/config.js`：local/test/staging/production 配置校验；staging 和 production 强制校验证书的数据库 TLS。
- `backend/.env.example`：不含真实密钥的本机配置模板；生产配置由云密钥服务注入。
- `backend/migrations/`：成对的正向和回滚 SQL；迁移器使用 PostgreSQL advisory lock 防止多实例重复迁移。
- `backend/Dockerfile`：生产镜像入口。
- `compose.backend.yml`：仅用于本机联调，不复用其中的账号密码到云环境。

本机两个容器使用 `unless-stopped` 策略，Docker Desktop 启动后会自动恢复；PostgreSQL 与 API 都有健康检查。该策略用于开发与联调便利，不替代生产环境的容器编排和多实例自愈。

本机启动顺序：先启动 PostgreSQL，执行 `pnpm backend:migrate`，再执行 `pnpm backend:start`。`/health/live` 只表示进程存活；`/health/ready` 只有数据库查询成功才返回 200。

## 3. 长期运行要求

- 生产使用托管 PostgreSQL 或独立数据库主机，数据库不开放公网端口。
- API 只接受负载均衡或反向代理流量；TLS 终止点使用自动续期证书。
- 数据库连接、微信密钥、令牌签名密钥和加密主密钥进入云密钥管理服务，不能写进镜像、仓库或启动日志。
- 至少运行两个无状态 API 实例；滚动发布前先执行兼容性迁移，旧版本和新版本可短时共存。
- 日志输出 JSON 到标准输出，采集 request ID、路由、状态码和耗时，不记录正文、Token 或个人密钥。
- 对健康检查、5xx、P95 延迟、数据库连接池、同步积压和迁移失败设置告警。

## 4. 备份与恢复

- PostgreSQL 开启每日全量备份和持续时间点恢复，首阶段目标 RPO 不超过 15 分钟、RTO 不超过 4 小时。
- 备份跨可用区保存，生产账号误删不能同时删除备份。
- 每月至少在隔离环境恢复一次，并核对用户数、灵感数、变更游标和关键关联。
- 对象存储启用版本和生命周期规则；数据库只保存对象键、大小和哈希。
- 发布前保留数据库迁移点和上一版镜像；代码回滚不能绕过数据库兼容检查。

## 5. 云迁移关卡

正式迁移前必须明确云厂商、部署地区、域名、备案状态、微信小程序合法域名、预计用户量和预算。之后按以下顺序执行：

1. 创建 production 网络、托管数据库、密钥和容器运行环境。
2. 在 staging 用生产同构配置执行迁移、回滚和备份恢复演练。
3. 配置域名、TLS、CORS、微信合法域名及访问限制。
4. 部署 API，验证存活、就绪、日志、指标和告警。
5. 使用两个账号完成小程序与 Web 的灵感创建、修改、冲突、删除和退出验证。
6. 分批迁移 Demo 本机数据，保留旧数据一个版本周期，并验证数量与关联。
7. 观察稳定后再启用项目、学习、工具和素材数据迁移。

未完成真实 staging 验证、恢复演练和双账号隔离前，不把云环境标记为可长期运行。

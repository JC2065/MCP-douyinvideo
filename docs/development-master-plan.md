# YOUAI 开发主导方案

版本：1.0 · 生效日期：2026-10-10 · 状态：后续产品与开发的主入口。

2026-10-12 专项执行路线见[云端创作与飞书资产矩阵规划](cloud-creation-roadmap.md)：沿用创作者与共用数据中台范围，当前最高优先是正式手机云端闭环；飞书管理与归档随后接入，商家与金额范围继续延期。用户确认目标进一步具体为可发布的视频成片、可复用中间资产和基于明确反馈的偏好优化。

本文是 YOUAI 当前阶段的执行依据。产品范围见[产品方案](product-plan.md)，服务设计见[多端数据中台](backend-data-platform.md)，Demo 字段拆分见[后端数据设计基线](demo-backend-data-design.md)，网页展示见[网页版设计](web-app-design.md)；专题文档与本文冲突时，先更新本文并记录决策，再开始编码。

机器可检查的功能状态保存在[功能登记表](feature-registry.json)。每项功能、接口、页面或重构都必须关联一个登记编号。

## 1. 唯一核心目标

帮助创作者把一个真实输入转化为可编辑、可保存、可继续使用的创作项目，并能在不同设备恢复。

核心闭环只有一条：

```text
灵感 / 学习案例 / 用户素材
            ↓
        创建创作项目
            ↓
   编辑脚本、分镜与工具产物
            ↓
     保存版本并标记完成
            ↓
       复盘产生新灵感
```

任何新功能都要回答它改善闭环中的哪一步、保存什么真实产物、失败后如何恢复。回答不了的功能不进入当前开发。

## 2. 不可偏离的产品原则

1. 一级产品结构固定为灵感、创作、学习、我的；微信小程序和 Web 可以采用不同布局，但含义一致。
2. 创作项目是业务核心容器。脚本、分镜、素材、工具结果、来源案例、版本和复盘不能各自成为孤岛。
3. 用户正常操作尽可能在小程序、Web 或后续 App 内完成。“我的”负责个人内容与设置，平台安全配置留在服务端。
4. 数据中台从登录会话确定用户归属。客户端不能声明 ownerId、user_id、管理员或其他授权身份。
5. 多端共用数据、API、错误码和纯业务规则；小程序、Web、App 分别实现适合设备的展示层。
6. 本机优先保存，在线后增量同步；重复请求不能产生重复数据，版本冲突不能静默覆盖。
7. 真实服务没有接通和验证前，只能标记为原型或待联调，不能用模拟结果宣称功能可用。
8. 商家、任务撮合、订单、金额（预算、收益、结算、支付和提现）和运营后台全部延期，不借本轮基础建设提前进入。
9. 优先交付纵向闭环：一次只让一条用户路径从界面走到真实存储并通过异常验证，再扩展横向功能。
10. 用户输入、草稿和历史版本优先于自动化便利。生成、重试、迁移或同步不能静默破坏已有内容。

## 3. 当前事实基线

| 层次 | 已有事实 | 当前限制 |
| --- | --- | --- |
| 微信小程序 | Demo 1.0 有灵感、创作、学习、我的及本机保存；仍残留历史任务原型 | 未接统一登录和生产数据中台 |
| 网页端 | 已有四入口响应式交互原型 | 只有演示数据，未接真实路由、登录与 API |
| 数据中台 | 已有 API 路由清单、无依赖领域规则及行为测试 | 不是 HTTP 生产服务，没有 PostgreSQL 实现 |
| 视频样例 | 本机 Python 服务可生成无声文字视频 | 不等于线上 AI 视频服务，未接账号和对象存储 |
| AI 与六工具 | 有配置和入口原型 | 多数没有真实服务调用、结果归档与生产验证 |

基线标签 `demo-v1.0` 保持不变。后续不能用“Demo 中可以点击”作为生产验收证据。

## 4. 功能状态与优先级

状态定义：

| 状态 | 含义 |
| --- | --- |
| baseline | Demo 基线已有并通过当前范围测试，但可能只有本机能力 |
| prototype | 有界面或本机原型，未通过真实后端与多端验证 |
| design_ready | 数据、接口、异常和验收已经定义，可以进入开发 |
| planned | 已确认需要，但依赖或设计尚未齐全 |
| blocked_external | 等待真实服务、凭据、部署或合规条件 |
| production_ready | 在 staging 和要求的真实客户端完成验收，可进入发布流程 |

优先级只有三档：P0 直接组成核心闭环；P1 提升闭环效率或复用；P2 在核心稳定后扩展。当前不接受“先做展示、以后再接数据”作为 P0 完成方式。

具体状态、依赖和验收见 `docs/feature-registry.json`。功能登记表中的状态变化必须和实现、测试证据一起提交。

## 5. 主导开发路线

### 阶段 A：统一身份与灵感纵向闭环

范围：CORE-01、CORE-02、INS-01、QA-01。

完成条件：真实微信登录建立统一用户；灵感可在断网时新增，恢复网络后同步；同一账号能在 Web 读取和编辑；另一账号无法感知数据；重复提交不重复；冲突保留两边内容。

这一阶段没有完成前，不接入新的在线工具，也不建设 App 页面。

### 阶段 B：创作项目和历史版本

范围：CRT-01、MY-01。

完成条件：从灵感建立项目，编辑脚本或分镜，保存多个版本，重开恢复；“我的”能管理项目与草稿；小程序和 Web 并发修改触发明确冲突，不覆盖旧稿。

### 阶段 C：学习应用闭环

范围：LEARN-01、LEARN-02。

完成条件：案例事实、分析和练习保持区分；收藏、笔记和进度真实同步；案例方法创建项目时保留来源，用户主题不会被案例内容冒充。

### 阶段 D：AI 与工具逐项接入

范围：CRT-02、CRT-03、MY-02。

每次只接一个工具或模型。必须有真实成功样本、失败样本、超时、重试、结果归入项目、重开恢复和权限验证。提词器基础阅读优先作为本机能力完成，外部接口不阻塞它。

### 阶段 E：多端发布准备

范围：WEB-01、QA-02；App 展示层另立功能编号。

完成条件：Web 从原型升级为真实客户端；同账号跨端继续编辑；关键流程具备响应式、键盘、无障碍和真实设备验证；监控、备份、恢复和数据迁移演练完成。

## 6. 接下来直接执行的开发包

下一轮从阶段 A 开始，按以下顺序执行，不并行扩张业务范围：

1. 建立可部署的后端工程和配置分层，加入 PostgreSQL 迁移框架、健康检查和请求标识。
2. 创建 users、user_identities、sessions、ideas、change_log、idempotency_keys 首批表和回滚迁移。
3. 实现微信登录交换、开发环境测试身份、访问令牌刷新、退出与 `/me`。
4. 实现灵感增删改查、幂等写入、版本冲突和增量变更接口。
5. 在小程序加入平台无关 API 客户端、本机仓库和同步队列，迁移现有灵感但不删除旧数据。
6. 将 Web 灵感原型接入同一接口，进行同账号交叉编辑和双账号隔离验证。

完成一个步骤后再进入下一个。数据库和身份方案未完成时，前端可以完善错误与加载状态，但不得继续增加业务页面。

## 7. 需求准入规则

一个需求只有同时满足以下条件才能进入开发：

- 关联一个现有功能编号，或先在功能登记表创建编号。
- 说明用户触发、输入、持久化产物和下一步动作。
- 列出加载、空数据、失败、重试、无权限、离线和冲突中适用的状态。
- 明确哪些客户端受影响，以及共享层与平台适配层的边界。
- 给出可复现的成功样本和至少一个失败样本。
- 不依赖延期范围，不把未确定的第三方能力当作事实。

需求只改善颜色、文案或位置时，也要说明它修复了什么可用性问题；没有证据的装饰性重做不进入近期计划。

## 8. 完成标准

功能只有满足以下条件才能从 prototype、design_ready 或 planned 升为 production_ready：

1. 真实数据路径已接通，权限由服务端执行。
2. 主流程和适用的异常流程通过自动化测试。
3. 受影响调用方、共享逻辑和跨端行为完成验证。
4. staging 使用真实类型输入完成至少一个成功样本和一个失败样本。
5. 页面重开、网络中断、重复点击和账号切换不会丢失或串用数据。
6. 数据迁移、回滚和清理方式已说明；不可逆操作有明确确认。
7. 用户界面只描述真实可用能力，原型或限制有准确说明。
8. 功能登记表、专题文档、测试批次和 Git commit 已同步。

只完成页面、只返回任务编号、只通过模拟测试、只在一个账号上成功，都不算完成。

## 9. 联调与发布关卡

| 关卡 | 必须验证 | 阻断发布的情况 |
| --- | --- | --- |
| 数据正确性 | 归属、版本、幂等、墓碑、迁移、备份恢复 | 串号、静默覆盖、重复记录、无法恢复 |
| 安全 | 会话、越权、凭据掩码、私有文件、日志脱敏 | 客户端可伪造归属、密钥进入日志或作品 |
| 小程序 | 开发者工具和真实微信设备、合法域名、授权拒绝 | 只在模拟器成功、真机无法保存或恢复 |
| Web | 桌面与移动视口、键盘、Cookie 会话、上传 | 原型数据被误认为真实、窄屏不可操作 |
| 跨端 | 同账号继续编辑、不同账号隔离、冲突处理 | 数据不一致且无提示、退出后残留上个账号数据 |
| 工具任务 | 成功、失败、超时、重试、状态恢复、结果归档 | 失败丢输入、重复执行、结果无归属 |

发布前按仓库 [AGENTS.md](../AGENTS.md) 执行测试批次规则。第 5 次汇总相关范围，第 10 次执行完整测试；必要的真机和浏览器验证不能由单元测试替代。

## 10. 变更控制

- 本文、功能登记表、产品方案、中台设计和网页版设计构成受控方案集。
- 新方向与当前原则冲突时，先修改主导方案，写明替换的决定和受影响功能编号，再修改代码。
- 同一次功能开发不得顺手加入无关页面、字段或角色；发现新需求时先登记到 planned。
- 每个 PR 或 commit 说明功能编号、用户结果、影响客户端、数据变化、测试和限制。
- 每个阶段结束后只根据真实使用与故障证据调整优先级，不以“看起来完整”增加范围。

## 11. 成功判断

首阶段先观察事实，不预设漂亮数字：用户是否成功保存第一条灵感；是否从灵感或案例创建项目；是否编辑并保存版本；是否在另一设备恢复；失败后是否继续完成；工具结果是否被项目复用。

当这条闭环在真实账号、真实网络和真实设备上稳定成立，才扩大工具数量、AI 能力和客户端范围。
